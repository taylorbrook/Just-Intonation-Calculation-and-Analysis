<!-- Locked decisions from CONTEXT.md that this plan must implement verbatim. -->

D-01: Host is **GitHub Pages** (not Cloudflare). Single repo, no new vendor.

D-02: Single GitHub Actions workflow. Order:
  1. `npm ci` (NOT `npm install` — deterministic install per package-lock.json)
  2. `npm run lint:types`
  3. `npm run test`
  4. `npm run lint`
  5. `npm run format:check`
  6. `npm run build`
  7. `actions/upload-pages-artifact` (artifact: `dist/`)
  8. `actions/deploy-pages`

  Steps 2–5 are deploy gates. A failure blocks step 7+.

D-03: PRs run steps 1–6 (build + gates). Steps 7–8 (upload-artifact + deploy) only on push to `main`. Implementation pattern: separate `build` job runs always; separate `deploy` job runs only on main with `if: github.event_name == 'push' && github.ref == 'refs/heads/main'`.

D-04: Default `*.github.io/<repo>` URL. NO custom domain wiring in Phase 1.

D-05: NOT using `observable deploy`. Use `observable build` → `dist/` → upload as Pages artifact.

D-10: Four gates ARE: `tsc --noEmit`, `vitest run`, `eslint .`, `prettier --check .` — all four MUST be present in the workflow.

D-11: NO pre-commit hooks. CI is the gate.

D-13: The `ci` script chains all four gates plus build, but the workflow runs each script SEPARATELY so failures are individually attributable in the Actions UI.

D-18: Node 20 LTS. `actions/setup-node` MUST set `node-version: '20'` (or read from `.nvmrc`; `node-version-file: '.nvmrc'` is preferred).

Specific guidance from CONTEXT.md `<specifics>`:
  - Use GitHub's OFFICIAL Pages workflow pattern: `actions/configure-pages` + `actions/upload-pages-artifact` + `actions/deploy-pages`. NO third-party deploy actions.
</key_decisions>

<security_constraints>
<!-- From <security_threat_model> in the planner brief -->

- `npm ci` (deterministic, uses package-lock.json) — NEVER `npm install` (which can drift).
- Only first-party GitHub actions: `actions/checkout`, `actions/setup-node`, `actions/configure-pages`, `actions/upload-pages-artifact`, `actions/deploy-pages`. No third-party.
- Pin actions to major versions (`@v4`, `@v5`) — this is the GitHub Actions community standard and gets security patches automatically. SHA-pinning is overkill for first-party actions in a personal-research-notebook context.
- The workflow's only secret is the auto-provided `GITHUB_TOKEN`. No third-party API keys in Phase 1.
- Permissions: minimum needed for Pages — `contents: read`, `pages: write`, `id-token: write`.

    Create the directory and file: `.github/workflows/deploy.yml`. Final contents (verbatim — adjust nothing without justification):

    ```yaml
    # Single GitHub Actions workflow for Tuning Systems.
    # Per Phase 1 CONTEXT.md decisions:
    #   D-02: npm ci → lint:types → test → lint → format:check → build → upload-artifact → deploy
    #   D-03: PRs run gates + build; only push-to-main runs upload-artifact + deploy
    #   D-05: NOT using `observable deploy` (deprecated); deploy via Pages actions
    #   D-18: Node 20 LTS, pinned via .nvmrc

    name: CI and Deploy

    on:
      push:
        branches: [main]
      pull_request:
        branches: [main]

    # Pages deploy permissions per GitHub's first-party recipe.
    permissions:
      contents: read
      pages: write
      id-token: write

    # Allow only one concurrent deploy; cancel in-progress runs of this workflow
    # but DO NOT cancel an in-progress deploy (let it finish so the live site stays consistent).
    concurrency:
      group: pages
      cancel-in-progress: false

    jobs:
      build:
        name: Build and run gates
        runs-on: ubuntu-latest
        steps:
          - name: Checkout
            uses: actions/checkout@v4

          - name: Setup Node 20
            uses: actions/setup-node@v4
            with:
              node-version-file: ".nvmrc"
              cache: "npm"

          - name: Install dependencies (deterministic)
            run: npm ci

          - name: Type-check (D-10 gate 1)
            run: npm run lint:types

          - name: Unit tests (D-10 gate 2)
            run: npm run test

          - name: Lint (D-10 gate 3)
            run: npm run lint

          - name: Format check (D-10 gate 4)
            run: npm run format:check

          - name: Phase 1 deny-list check (D-21)
            # Defense-in-depth: ensure forbidden packages haven't slipped into package.json.
            run: |
              node -e "const p=require('./package.json'); ['temperaments','mathjs'].forEach(k=>{if((p.dependencies||{})[k]||(p.devDependencies||{})[k]){console.error('FORBIDDEN dep present:',k); process.exit(1)}})"

          - name: Build static site
            run: npm run build

          - name: Configure Pages
            if: github.event_name == 'push' && github.ref == 'refs/heads/main'
            uses: actions/configure-pages@v5

          - name: Upload Pages artifact
            if: github.event_name == 'push' && github.ref == 'refs/heads/main'
            uses: actions/upload-pages-artifact@v3
            with:
              path: dist

      deploy:
        name: Deploy to GitHub Pages
        # D-03: deploy only on push to main, never on PRs.
        if: github.event_name == 'push' && github.ref == 'refs/heads/main'
        needs: build
        runs-on: ubuntu-latest
        environment:
          name: github-pages
          url: ${{ steps.deployment.outputs.page_url }}
        steps:
          - name: Deploy
            id: deployment
            uses: actions/deploy-pages@v4
    ```

    Notes for the executor:

    - The directory `.github/workflows/` may not exist yet — create it with `mkdir -p .github/workflows` before writing the file.
    - The `node-version-file: ".nvmrc"` directive reads the Node version from the file Plan 01 wrote (`20`). This keeps `setup-node` and `.nvmrc` in lockstep — bumping Node is a one-file change.
    - The deny-list step is defense-in-depth against D-21 — the same check runs locally in Plan 03's Task 1 acceptance criteria, but having it in CI means a future PR that adds `temperaments` or `mathjs` is rejected automatically.
    - `cache: "npm"` enables the actions/setup-node-managed npm cache (uses `package-lock.json` as the cache key). Saves install time on repeat runs.
    - The `upload-pages-artifact@v3` step's `path: dist` matches `observable build`'s output directory (default).
    - The `deploy` job's `environment` block ties the run to the `github-pages` environment, which GitHub auto-creates on first deploy. The `url` output makes the deployed URL visible in the Actions UI.
    - PR runs: only the `build` job runs (the deploy job's `if:` excludes PRs). Within the `build` job, `configure-pages` and `upload-pages-artifact` are also gated to push-to-main. So PRs run gates + build but produce no artifact and no deploy — exactly D-03.

    DO NOT add:

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| GitHub Actions runner ↔ npm registry | Workflow runs `npm ci` against the locked dependency tree. |
| GitHub Actions ↔ GitHub Pages | First-party token-bound deploy via OIDC (`id-token: write`). |
| Repo `main` branch ↔ live site | Every push to main updates the live site; gate failures block the deploy. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-01-13 | Tampering | Non-deterministic install in CI | mitigate | Workflow uses `npm ci` (NOT `npm install`) which fails fast if `package-lock.json` is out of sync — preventing silent dep drift in CI vs. local. |
| T-01-14 | Tampering | Third-party GitHub Action with malicious code | mitigate | Workflow uses ONLY first-party `actions/*` (checkout, setup-node, configure-pages, upload-pages-artifact, deploy-pages). No third-party actions. Per CONTEXT.md `<specifics>`. |
| T-01-15 | Information Disclosure | Workflow logs leaking secrets | accept | Phase 1 has no third-party secrets. The auto-provided `GITHUB_TOKEN` is masked by Actions automatically. |
| T-01-16 | Elevation of Privilege | Excess permissions on the workflow | mitigate | `permissions:` block scoped to minimum needed: `contents: read` (checkout source), `pages: write` (deploy), `id-token: write` (OIDC for Pages). No `actions: write`, `packages: write`, `contents: write`. |
| T-01-17 | Denial of Service | Concurrent deploys racing | mitigate | `concurrency: { group: pages, cancel-in-progress: false }` ensures only one deploy runs at a time and existing deploys complete before new ones start (so the live site never stalls in a half-deployed state). |
| T-01-18 | Spoofing | Forked-PR running with elevated permissions | mitigate | The deploy job's `if:` requires `github.event_name == 'push' && github.ref == 'refs/heads/main'`. PRs (including forked) only run the `build` job, which has no Pages-write permissions effective (the gate excludes them from upload-artifact + deploy steps). |
| T-01-19 | Tampering | Forbidden packages slipping into deps | mitigate | Workflow contains a step that scans `package.json` for `temperaments` / `mathjs` and exits 1 if found (D-21 enforcement). Defense-in-depth alongside Plan 03's local check. |
</threat_model>
